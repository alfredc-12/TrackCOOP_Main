**Continuation, 8 November 2026:** The owner explicitly confirmed the configured remote AWS RDS schema `trackcoopdb_main` is development-only and unused by live users, applications, payment services, or email workers. A read-only connection reported MySQL 8.4.9 and 91 base tables, including the principal membership, financial and ledger tables. The original local configuration enables PayMongo Test Mode, Resend email and S3 storage and includes live-payment credentials; the test launcher clears these credentials, disables payment and email, uses local storage, restricts routes, and blocks outbound connections except to the confirmed database. It listens on loopback only. The configured MySQL connection does not use TLS; the workload traverses the network to the remote development database, and latency includes this topology. The old local MySQL environment above was not restarted or modified during this continuation. The laptop reports 16 GiB installed memory, 15.21 GiB visible physical memory, and a fixed 512 GB disk; available memory varied during testing and disk performance was not benchmarked.

The JMeter binary archive came from `https://dlcdn.apache.org/jmeter/binaries/apache-jmeter-5.6.3.zip`. Its SHA-512 was compared with Apache's published checksum. JMeter 5.6.3 starts with plugin-scanning and Windows Java preferences warnings. Java 25 could start JMeter but its Groovy scripts failed compilation during CAL01; subsequent tests use checksum-verified Eclipse Temurin JRE 17.0.21+9. Windows reports version 10.0.26300. Node is 24.15.0.

The normal global limiter remains 500 requests per 15 minutes per IP and the login limiter defaults to 10 per 15 minutes. In the test-only wrapper, `TRUST_PROXY=true` and a local gate maps each validated synthetic client slot to a distinct reserved benchmarking address, overwriting any forwarded header. This models independent clients instead of making all virtual users share one source IP. The application limiters and authentication remain enabled, but the topology and trusted-proxy configuration differ from the ordinary launcher and must be disclosed in interpreting results. The test gate accepts only selected GET routes and POST login; a financial POST and payment POST were rejected with 403 and unauthenticated `/auth/me` with 401. An initial sequence with one-second think time encountered genuine 429 rate-limit responses during the third run after prior calibrations and repetitions. Those runs are preserved as invalidated setup evidence due to the credential-isolation issue described below; the subsequent plan uses a two-second think time to keep an individual synthetic user's maximum request frequency below 500 per 15 minutes, without changing or disabling the limit. Consequently the later results do not evaluate continuous one-second request pacing or its rate-limit behaviour.

The 20 JMeter identities use dedicated random credentials in ignored `scratch/jmeter-private/users.csv`. Their roles are four chairmen, four bookkeepers and twelve approved true members. The 5-, 10- and 20-user levels use the first 5, 10 and 20 rows, preserving the same one-chairman, one-bookkeeper, three-member ratio. The startup database schema lacked the activity-management migration: the initial route returned 500 with missing `activity_time`. On the owner-confirmed dummy database, the reviewed additive `20261108_activity_management.sql` was applied after verifying its columns and foreign-key prerequisites. It added three fields and the separate managed-attendance table; activity counts stayed 51 and participation counts stayed 4,629. No financial data was changed by the migration.

CAL01 produced no samples because Java 25's class version was unsupported by bundled Groovy. CAL02 uncovered a Groovy condition parsing bug in the test plan and is invalid for coverage. The corrected CAL03 covered J01–J10 in 282 HTTP samples with no assertion failures and generated an HTML dashboard. CAL04 deliberately changed one status assertion and correctly recorded the expected test failure. Dashboard reads populated missing referral codes on three new synthetic profiles; the remaining nine were initialized on those test-owned profiles before formal baselines. This observed dashboard write is not a financial operation and must not be described as a wholly read-only workload. Login also creates sessions and audit records.

After the first three 5-user executions started, inspection found that the application's dotenv loader could repopulate live-payment credentials into the local test process even though PayMongo was disabled, the route gate blocked payment requests and the network guard blocked external egress. The three runs are retained as invalidated safety-setup evidence. The corrected launcher changes into a private directory with no `server/.env`, clears integration credentials, and validates the parsed integration configuration before listening. Separate calibrations followed this correction.

CAL05 exercised the corrected launcher at two-second pacing. After adding a startup self-check for the outbound guard and J05 owner assertions, CAL06 exercised all ten groups with 177 HTTP samples, zero failures, an HTML report and matching pre/post protected-table checks. CAL07 failed before sending requests because its negative-test plan was not generated. CAL08 deliberately changed the expected synthetic member code and recorded the intended J05 ownership assertion failures; it is a negative test, not a performance failure.

The first two executions with the corrected launcher were also invalidated after review discovered that two integrity queries used the ledger status `Posted` for the distinct financial-record status field, whose active value is `Active`. Their original JTLs and snapshots are retained under `invalidated/integrity-query-version/`. The corrected integrity script checks active approved rental/POS source duplicates, protects financial-category checksums, and uses the application's operating and capital predicates to detect overlap. Preflight reported zero overlap and 10 active approved capital-tagged income-type records; those labels alone are not proof of operating-income inclusion. The corrected checks are targeted and do not establish every accounting or reporting invariant.

The data directory was newly initialized, and the instance reported `@@port=33328`, `@@bind_address=127.0.0.1`, and the specified data directory. The initial database list contained only `information_schema`, `mysql`, `performance_schema`, and `sys`. The import script checked those facts, created a new schema, verified the selected schema and instance again, and imported the repository base schema. A second execution correctly refused because a non-system schema existed. The server was shut down after preparation. It was started without MySQL X Plugin after the first startup showed that plugin binding to `::`; that first instance was immediately shut down. The local instance has an empty root password and must only be started bound to loopback with X Plugin disabled. No fixtures, ledger backfill, or additional migrations have been applied, and the environment is not ready for testing.

The standard API entry point binds to `0.0.0.0`; use a dedicated local test launcher binding `127.0.0.1`, with independent configuration validation, before starting the API. The application loads `server/.env` relative to its working directory, so the test process must run from a controlled directory and must not inherit real credentials. Relevant consumed settings include `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_SSL`, `PAYMONGO_ENABLED`, `PAYMONGO_MODE`, `PAYMONGO_API_BASE_URL`, `EMAIL_DELIVERY`, `STORAGE_DRIVER`, `LOCAL_STORAGE_ROOT`, frontend/CORS origins, and webhook settings. The PayMongo client validates that it is enabled before its calls, but no end-to-end egress isolation test has been performed. A network guard plus explicit localhost-only payment URL and rejected secrets must be verified before testing. Do not reactivate any webhook.

The API applies a global 500-request per 15-minute IP limit, and its default login limit is 10 per 15 minutes. A single-IP workload may trigger these controls; preserve and interpret resulting 429s, and document any justified test-only configuration change and its effect. No security setting was changed. No app or performance workload was started.
