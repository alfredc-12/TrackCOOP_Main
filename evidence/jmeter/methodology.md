# Planned methodology — not executed

Nine separate runs: three repetitions each at 5, 10, and 20 total concurrent users, each with a 60-second ramp-up and a subsequent 300-second steady measurement. The active-thread history must establish whether the target was reached and maintained. Filter steady-state samples by recorded timestamps, documenting the rule for requests crossing boundaries. Track authentication and workflow transaction samples separately from HTTP samples; avoid double counting parent transactions.

The executable plan uses one thread group, a two-second per-request think time, and a fixed role sequence repeated every five threads: one chairman, one bookkeeper, three members. Each thread authenticates once using its own CSV row and cookie. HTTP samplers are labeled `J01`–`J10`; separate transaction summary samples are labeled `TX_Jxx` and excluded from HTTP statistics. Thread-group duration is 365 seconds: 60 seconds of ramp, the following 300 seconds of steady measurement, then a five-second tail that is excluded from acceptance statistics. The start of the window is 60 seconds after JMeter's recorded test start. A sample is included only if it both starts and finishes within the window. Logged thread start/finish times are used to verify continuous coverage across the complete measurement window.

Requests use a fixed sequence per applicable role, so each role repeatedly visits its assigned workflows instead of selecting the next request according to response speed. Different roles have different sequences, and slower workflows lengthen their cycles; measured group proportions must be reported. Login creates session and audit records. A first member-dashboard read can initialize a missing referral code; all test-owned profiles are initialized before formal baselines. Payment and financial write operations are excluded; no claims are made about their load behavior. No expected 4xx is included in formal traffic, so unexpected failed sampler assertions count as errors.

Before and after every run the integrity script performs aggregate queries and `CHECKSUM TABLE` on selected tables. These scans can warm database caches; the workload should therefore be interpreted as a repeated warm-development-environment evaluation, not a cold-start measurement. The scans also generate database activity outside the JMeter timing window.

For each run and group calculate sample count, failures, response-time distribution, mean, median, nearest-rank P90/P95/P99, population standard deviation, bytes, and completed HTTP samples divided by the actual 300-second measurement interval. Record unexpected failure percentage as unexpected failures divided by applicable requests. Expected rejections require explicit assertions and separate counts. Compute overall percentiles from underlying samples, not averages of group percentiles. Distinguish the mean of three run-level percentages from the pooled failure count divided by pooled applicable requests.

For every run, evaluate steady-state P95 at 3,000 ms for 5 and 10 users, 5,000 ms for 20 users; unexpected error rate at most 1%; and zero critical integrity failures. Missing data or unverified checks mean **Not Evaluated**, not a pass. Inspect critical group metrics separately. Short tests cannot establish long-term reliability or production capacity.
