# PR 1B: controlled budget foundation

This is an internal foundation, not an active posting policy. No existing route, finance posting path, budget transition, or policy activation calls it. Legacy budget behavior and its known fail-open and historical-accounting issues remain unchanged until the reviewed PR 1C integration.

## Assignment and accounting

For date/category/season, `selectBudgetLine` selects approved, date-covered lines for the category. A unique exact-season line wins over any general line; otherwise a unique general line wins. Multiple matches in the selected tier produce `AMBIGUOUS`, and none produces `UNBUDGETED`. No arbitrary overlap tie-break is introduced. The line ID is the stable attribution key, not a later recomputation. Category and source eligibility continue to follow the canonical operating predicate.

The additive `budget_expense_assignments` table stores at most one line per financial record, actor and timestamp. It is empty after migration: no historic record is silently assigned. Approved, Active, eligible expenses count as posted only against their recorded line, including seasonal expenses assigned to a general line. Assigned Active unapproved expenses are drafts unless explicitly marked `Pending`; pending is presented separately. Voided, reversed and non-expense rows do not consume spend. Eligible historical expenses without an assignment, and assigned rows whose current classification/date/category/season no longer agrees, block as `HISTORICAL_ATTRIBUTION_REQUIRED`. The check is deliberately conservative: suspicious or superseded Active rows may require review rather than being silently excluded. The preview returns unresolved counts, not an attribution decision. Closed and amended historical budgets require evidence-based review; the migration does not rewrite them. Unassigned drafts cannot be assumed to be commitments.

Amounts are decimal strings processed as integer centavos. Posted spend, drafts, explicit pending, remaining and projected spend remain separate. A hard limit blocks when projected posted spend exceeds it; a warning threshold never overrides a limit. Because the cooperative has not decided whether pending commitments reserve capacity, any explicit pending amount blocks the controlled post as `COMMITMENT_POLICY_REQUIRED`. This is a safeguard, not a policy choice. Ambiguity, unknown historical attribution, stale basis, absent budget, and unavailable/schema-failed evaluation also block. The current legacy evaluator is not changed.

## Transaction and concurrency contract

`previewControlledBudget` is an internal, read-only assessment and returns the selected line's fingerprint. `withControlledBudget` starts a transaction, locks the single guard mutex and relevant current budget rows, rechecks assignment, fingerprint, approved status, history, commitments and centavo-exact capacity. It calls an internal future posting callback only if the guard passes. Before commit it verifies the callback's posted financial record matches the guarded date, category, season and amount and passes canonical operating eligibility; then it inserts the unique record-to-line assignment, audit event and an idempotency receipt in the same transaction. Duplicate operation keys replay the saved reference; reuse with different parameters fails. Exceptions roll back the transaction. Callbacks and their record writes must use the supplied transaction connection; this API is not mounted as a route.

**Activation blocker:** the mutex only serializes *cooperating* writers. Existing financial writes and budget create/approve/close paths do not yet acquire it. The MySQL race test covers cooperating guarded writers and a simulated cooperating close, not the existing legacy transition. PR 1C must acquire this same lock across every controlled writer and relevant budget approval, amendment and closure, revalidate policies and identity within the same transaction, and perform the legacy/alternate-path, phantom-overlap, post-versus-close and direct-write concurrency tests before activation. It must ensure every pending commitment is explicitly tracked, decide how commitment capacity is governed after cooperative approval, and complete historical attribution/cutover reconciliation. Existing source-owned POS, rental, gateway and capital settlement remains outside a generic manual-finance override.

## Migration and evidence

`20261106_budget_attribution_guard.sql` adds assignment, coordination and idempotency tables with foreign keys and a single mutex row. It performs no backfill. The owner-attested export shows existing `financial_records.financial_record_id`, `budget_lines.budget_line_id`, and `users.user_id` are BIGINT UNSIGNED; it does not prove the current target schema or installed migration state. Before any separately authorized deployment, check actual DDL, migration history, indexes, source data, storage, target isolation and restore procedure. MySQL DDL commits independently; restore from a managed backup or apply a reviewed forward correction rather than dropping tables with live attribution. No automatic migration application is authorized.

The focused MySQL test requires explicit `BUDGET_GUARD_ISOLATED_MYSQL=1`, a loopback port and a datadir containing the dedicated synthetic marker; it verifies the running server's actual datadir and port before creating a fresh randomly named `_test_` schema. It uses only synthetic rows and does not delete the test schema. Run only against a separately initialized disposable instance. Never point it at staging, production or an existing data directory. The repository's usual CI does not automatically run this opt-in test.
