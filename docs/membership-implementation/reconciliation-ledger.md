# PR #7: application capital reconciliation ledger posting

This correction belongs to Section 1 / PR #7 only. It changes `reconcileApplicationCapital` and its tests, not PR #6’s capacity helper or financial-integrity implementation.

## Behavior

The caller’s existing transaction now locks the member row, preserves/inserts missing validated application payment rows, and calls the existing `postShareCapitalPaymentToLedger` for every validated reference. The same transaction then links payment/financial records as before.

Posting visits previously reconciled payment rows as well as newly inserted ones. The shared ledger function’s `(source_type, source_id)` identity makes retries and existing credits idempotent. Payment date, amount and original reference are retained; existing ledger records are not overwritten. Member ownership, payment validation status and amount must agree before posting. An inconsistent historical payment row is rejected for review rather than silently corrected.

Any posting/ceiling failure rolls back newly inserted payment rows, account/ledger changes and links. No production repair job, historical bulk update, SQL migration, gateway change or deployment is included.
