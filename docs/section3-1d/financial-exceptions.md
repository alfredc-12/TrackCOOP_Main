# PR 1D financial exceptions — inactive source-safe foundation

Cases reference existing authoritative source IDs; they never post, validate, reverse, refund or settle a payment. The taxonomy in `finance-exception.model.ts` includes posting, source/amount, receipt, evidence, budget/policy, stale approval, unbudgeted, correction, historical attribution, processing, late-event and critical privacy/gateway/capital concerns. An unsupported/manual classification is a **reported concern**, not proof an incident occurred. No public endpoint accepts raw webhook data, file contents, free text, account numbers, tokens or arbitrary metadata; structured reason codes are used instead.

State: `Open -> Under Review / Awaiting Evidence / Escalated -> Resolved -> Closed`; `Resolved` or `Closed` can reopen. **Resolution and closure are disabled for all cases** with `EXCEPTION_SOURCE_COORDINATION_REQUIRED` until cross-source synchronization is proven. Detection is informational; unsupported, unavailable or ineligible conditions are `unknown` and cannot establish clearance. A pending payment is never treated as a missing posting. Missing/duplicate/mismatch detection is limited to validated POS/Rental payment references with an existing, eligible, linked source entity; POS accepts `pos_sales` and legacy `POS_SALE`, rental accepts `rental_bookings`. Detection requires the payment reference, correct source module, source record ID, active approved income status and source category (`POS_SALES` or `RENTAL_INCOME`), with amount compared in SQL. Inconsistent source link/status or unavailable source data is unknown. A wrong-source or Manual ledger row cannot satisfy or duplicate a legitimate posting. Rental bookings whose current payment-reference pointer differs are conservatively unknown (including historical/partial cases). Receipt detection requires validated/reversed references. The absence of a match does not establish correctness for other sources. Failure to query the authoritative source does not permit closure.

Both staff roles can create/investigate cases and assign active staff; members cannot access cases. A Chairman must resolve/close High and Critical cases and review/resolve escalated cases. Every update checks an expected version and requires an action-specific reason code. Source fingerprint `(type,id,code)` deduplicates cases; request keys are stored in append-only event rows to detect conflicting retries. Repeated detection creates an event rather than a new case. Reopening does not delete old events. An event stores actor, role, action, state transition, reason code, timestamp and assignment; the case provides source identity and code. No generic case endpoint performs financial mutation.

`20261107_finance_exception_cases.sql` adds case and append-only event tables with user FKs, unique fingerprint and event version/request keys; no source or financial table is changed and no backfill is performed. MySQL DDL is nontransactional: review actual target schema and migration order, test on a disposable database and prepare managed restore/forward correction before any separately authorized deployment. No retention duration or purge policy is invented.

## Review and release blockers

- **Fail-closed restriction:** all `resolve` and `close` actions return `EXCEPTION_SOURCE_COORDINATION_REQUIRED`; no case can newly become Resolved or Closed through this API. Existing POS, rental, gateway, payment-reference, receipt, legacy-finance and controlled-finance writers do not all share an exception lock. Before enabling closure, verify source ownership, transaction isolation, indexed range/phantom locks and writer participation with Section 4 review and real source-service races. Detection is an observation, not a durable clearance certificate.
- Generic reported concerns with no implemented authoritative detector deliberately cannot resolve or close. Full evidence links need PR 1E; reconciliation and close need PR 2D. No generic correction, retry or source settlement is implemented.
- The single permanent fingerprint reopens a closed case on verified recurrence; historical conditions remain in its event chain. Source references are polymorphic and checked by the service, not enforced by a cross-table FK. Orphan monitoring and cross-source ownership require later review.
- PR 1C controlled finance remains inactive. The PR #13 broad financial-publication disclosure issue remains a release blocker. Historical attribution, cooperative policy and actual target schema remain unverified.

## Lock order and source contracts

For existing cases, mutations lock the case row first, then (when detection/reopening needs it) the payment or source row, then the event request-key row. Assignment locks case, event key, then assignee. New fingerprints lock the unique fingerprint lookup first; gap-lock conflicts are safely reported for retry. MySQL deadlocks, lock timeouts and duplicate-key races in creation, transitions and assignment become HTTP 409 `EXCEPTION_CONFLICT`. No isolation level or gap lock is claimed to protect unrelated writers. POS cash/QRPH use source module `POS` and POS sale ID; rental cash/QRPH use `Rental` and booking ID. Legacy finance can edit/post linked records independently; receipt generation/retry updates receipt processing independently. These services retain their existing authority and are not modified by this PR.
