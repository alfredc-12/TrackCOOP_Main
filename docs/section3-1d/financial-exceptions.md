# PR 1D financial exceptions — inactive source-safe foundation

Cases reference existing authoritative source IDs; they never post, validate, reverse, refund or settle a payment. The taxonomy in `finance-exception.model.ts` includes posting, source/amount, receipt, evidence, budget/policy, stale approval, unbudgeted, correction, historical attribution, processing, late-event and critical privacy/gateway/capital concerns. An unsupported/manual classification is a **reported concern**, not proof an incident occurred. No public endpoint accepts raw webhook data, file contents, free text, account numbers, tokens or arbitrary metadata; structured reason codes are used instead.

State: `Open -> Under Review / Awaiting Evidence / Escalated -> Resolved -> Closed`; `Resolved` or `Closed` can reopen. Resolution/closure requires a fresh source check of an implemented condition; unsupported, unavailable or ineligible conditions are `unknown` and cannot resolve or close. A pending payment is never treated as a missing posting. Missing/duplicate/mismatch checks are limited to validated POS/Rental payment-reference operating postings; receipt checks require validated/reversed references. The absence of a match does not establish correctness for other sources. Failure to query the authoritative source does not permit closure.

Both staff roles can create/investigate cases and assign active staff; members cannot access cases. A Chairman must resolve/close High and Critical cases and review/resolve escalated cases. Every update checks an expected version and requires an action-specific reason code. Source fingerprint `(type,id,code)` deduplicates cases; request keys are stored in append-only event rows to detect conflicting retries. Repeated detection creates an event rather than a new case. Reopening does not delete old events. An event stores actor, role, action, state transition, reason code, timestamp and assignment; the case provides source identity and code. No generic case endpoint performs financial mutation.

`20261107_finance_exception_cases.sql` adds case and append-only event tables with user FKs, unique fingerprint and event version/request keys; no source or financial table is changed and no backfill is performed. MySQL DDL is nontransactional: review actual target schema and migration order, test on a disposable database and prepare managed restore/forward correction before any separately authorized deployment. No retention duration or purge policy is invented.

## Review and release blockers

- Source rechecks lock the payment reference, but existing source-owned writers are not universally guaranteed to acquire that same lock. A simultaneous source/ledger mutation can race with exception resolution. Atomic closure across those writers and durable stale-condition detection remain **unproven**; do not claim complete reconciliation or enable unattended closure. Cross-module review and race tests against the real source contract are required.
- Generic reported concerns with no implemented authoritative detector deliberately cannot resolve or close. Full evidence links need PR 1E; reconciliation and close need PR 2D. No generic correction, retry or source settlement is implemented.
- The single permanent fingerprint reopens a closed case on verified recurrence; historical conditions remain in its event chain. Source references are polymorphic and checked by the service, not enforced by a cross-table FK. Orphan monitoring and cross-source ownership require later review.
- PR 1C controlled finance remains inactive. The PR #13 broad financial-publication disclosure issue remains a release blocker. Historical attribution, cooperative policy and actual target schema remain unverified.
