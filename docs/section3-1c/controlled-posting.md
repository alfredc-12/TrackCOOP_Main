# PR 1C: inactive controlled posting workflow

This implementation is **not ready for activation**. The runtime router constructs the repository with an inactive gate and an evidence verifier that always reports unavailable. The injectable gate and evidence verifier in the repository are for isolated synthetic tests only; the gate also requires `NODE_ENV=test`, there is no runtime configuration or HTTP action that enables them. The test seam must not be wired to a production setting. A separate inactive-mode hook used by the legacy finance and budget repositories is likewise test-injected; it does not provide an activation endpoint. No organizational threshold, restricted-category schedule, commitment policy or activation decision is supplied by this change.

```text
DRAFT -> INCOMPLETE_EVIDENCE | CONFIGURATION_BLOCKED | BUDGET_BLOCKED
      -> ROUTINE_POST_ELIGIBLE -> POSTED -> CORRECTION_REQUESTED
      -> PENDING_APPROVAL -> REJECTED -> reasoned financial revision -> DRAFT
                          -> UNBUDGETED_REVIEWED -> fresh evaluation
                          -> APPROVED_FOR_POSTING -> POSTED
```

With the synthetic gate enabled, a Bookkeeper can atomically create a new Active, unposted manual income/expense record and its operation; production draft creation is disabled while inactive because the legacy budget calculation currently counts some unposted Active expenses. An operation can also be attached to an existing owned manual draft; its creation key is unique and bound to the request. A Bookkeeper can reevaluate a draft or blocked case. An authorized independent Chairman must give a reason and decide an unchanged Pending Approval case. Record fields, server-verified evidence identity, policy versions and budget basis are fingerprinted/rechecked; missing or changed inputs deny approval. Configuration Blocked cannot be approved. Ordinary evaluation cannot reopen a rejected operation. Its maker must provide a reason and revise at least one financial fact (category, type, season, amount or date); note-only and record-number-only edits do not qualify. If the rejected record changes outside this workflow, resubmission is blocked for review. A valid revision appends a distinct `resubmitted` event and preserves the original rejection actor and reason. Evidence-only resubmission remains future PR 1E work. A correction request for a controlled or legacy posted manual record records a reason and event without altering the original posted record; actual correction/reversal execution is not implemented here. Existing financial-record enum and posted totals are unchanged.

Only unlinked `Manual` records with no member or source reference and no capital classification are accepted by this generic path; member-linked and source-owned records need their established services. For a synthetic gate only, manual expense posting uses the 1B budget guard: one serialized transaction rechecks budget, policy, evidence, operation version and record, conditionally posts once, then records assignment, workflow/audit events and an idempotency receipt. Manual income uses the same global mutex and idempotency store, without treating income as budget spending. The budget guard now verifies that its record is an Expense, and binds the idempotency hash to the controlled operation ID. Idempotency prevents replay of one operation; it cannot prove that two separately keyed manual entries describe the same real-world event. The production gate always denies posting. An approved or routine operation is not a guarantee of later posting: all inputs must be rechecked at commit.

## Review and activation blockers

1. PR 1E must provide a transactionally verified, source-bound evidence adapter; a client-supplied Boolean is never sufficient. Runtime cases remain `INCOMPLETE_EVIDENCE` until this exists.
2. The actual runtime mode is hardcoded Inactive and is not atomically coordinated with an activation manifest; the synthetic gate and the legacy-mode hook are separate test seams, not a production activation mechanism. Simulated Active tests block the mapped finance repository routes and serialize budget repository create/transition; there is no reviewed persistent activation manifest or mode-change transaction. Alternate/direct writers, source contracts, budget amendments and phantom overlap races must be reviewed and integrated before activation.
3. Historic expense attribution and the cooperative decision on pending-commitment capacity remain unresolved. The 1B guard blocks unknown attribution, pending commitments, no budget and ambiguous budget lines. A Chairman can acknowledge an unbudgeted case as `UNBUDGETED_REVIEWED`, which is not posting authorization and cannot be posted through the 1B guard; an approved budget line or separately approved governance path is needed, followed by a fresh evaluation and any newly required independent approval.
4. Adjustment posting and execution of correction/reversal requests are not implemented. Source-owned reversals must remain in their source services; manual correction requires a separately reviewed linked offset/replacement workflow.
5. No cooperative-approved threshold or restricted schedule exists. Absent/draft/invalid/future/stale values block; an explicitly approved empty restriction schedule is valid only for restrictions.
6. The publication disclosure risk from PR #13 remains a separate release blocker. No target schema/migration history or staging/production behavior has been verified.

The additive migration `20261106_controlled_finance_workflow.sql` creates operation and append-only event tables with record/user FKs and uniqueness for source record and creation key. It performs no backfill and does not change existing enums. MySQL DDL is not transactionally reversible; before any separately authorized deployment, verify PR #14/#15 migration compatibility and exact target DDL, rehearse on disposable MySQL, and prepare managed restore or a reviewed forward correction. Never run reset SQL on an installed database. Synthetic tests do not establish live schema correctness.
