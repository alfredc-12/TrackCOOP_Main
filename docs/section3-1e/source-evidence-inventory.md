## Read-only receipt diagnostic in this draft

The experimental receipt diagnostic router is **not mounted in the application**: role-only access is insufficient and no source-scoped authorization or sensitive-read audit is in place. Its test-only diagnostic examines fully paid cash POS references and private local files; rental and noncash sources remain unsupported until their source-specific settlement and amount semantics are established. A matching result is explicitly branded `diagnostic` with status `observed_match` and an `observationHash`, not a finance verification result or fingerprint. It is not wired into controlled finance and must not be interpreted as bank settlement or approval evidence.

**Source metadata:** `createCentralDocument` now writes the supplied source metadata prospectively in the caller's transaction. The owner-attested structure export contains these columns, although historic migrations dropped them on other schema states. This does not establish provenance for old documents or provide unique, immutable relationship history. Target-compatible migration and source-writer tests remain required; do not fabricate metadata or bulk backfill.

The opt-in disposable MySQL producer test calls the actual receipt service for a synthetic rental payment, checks stored source metadata and retry behavior, checks that the diagnostic reports rental unsupported, and verifies that an audit insertion failure rolls back the document and receipt link. Its tables reproduce only the columns needed by the test, without full production constraints: it does not establish installed-schema compatibility, concurrent uniqueness, immutable storage, rental amount semantics, or a verified approval basis.

The file metadata and bytes are read outside a shared transaction with source and storage mutation. The status is a point-in-time diagnostic, not an approval or posting authorization; do not wire it to PR 1C until immutable source-bound links, private object versioning and race-safe rechecks exist. PR 1E is incomplete: secure creation/replacement/revocation, member self-service, source-authorized upload/download, payment and controlled-operation linking, S3 validation, exception evidence, and a trusted controlled-finance adapter are not implemented. Full privacy and target-schema tests remain blockers.

**Privacy and integrity blockers:** the unmounted diagnostic has no dedicated sensitive-read audit or job-scoped access. Local reads now use one no-follow file handle with identity and mutation checks, and fail closed when the platform lacks no-follow support. This still cannot guarantee immutable objects or prevent all parent-directory races and concurrent in-place writes; S3 ACLs and object versioning are unverified. Therefore no result may be used as approval evidence and the endpoint must remain unmounted until these controls are implemented and independently reviewed. Existing legacy receipt metadata gaps are not proof that any particular stored receipt is invalid or exposed.

## Restricted manual-draft relationship foundation

`20261107_manual_finance_evidence_links.sql` adds two tables. The links table references an existing financial record, document and creator, captures document version/checksum, preserves predecessor links, enforces one active link per record, and forbids reuse of any document identity in this relationship history. The events table records link/replacement/revocation, version, actor, request key/hash and reason. Events are append-only through the repository API; database privileges or triggers do not make them immutable against privileged SQL. The migration assumes compatible `users`, `financial_records`, and `documents` BIGINT keys and the G0 document columns; it has not been tested on the installed target. Rollback after use requires retaining relationship/audit history; do not drop tables as an ordinary rollback. No backfill is performed.

An additional disposable MySQL rehearsal creates the exact `users`, `documents`, `financial_records` and `payment_receipts` CREATE TABLE definitions from the SHA-256-matched owner-attested structure export, adds their primary keys, then installs the evidence and receipt-attempt migrations and checks their foreign-key parents and generated slot. It does not recreate the complete export, all parent foreign keys/indexes, migration ledger, historical data, or deployed target; those remain unverified. The global document uniqueness applies only within the manual-evidence table and is a deliberately conservative restriction, not a proven general evidence-sharing policy.

The **unmounted** `createManualEvidenceRepository` supports link, list, replace, revoke, event history and independent status checks for unposted, active manual financial records without member, source or payment links. A Bookkeeper can mutate only their own draft and attach only their own active, non-member, unexpired `Bookkeeper-only` Receipt/Financial Document with an existing checksum/version and no other source metadata; a Chairman can read this restricted history. Other staff, members and Associates have no access through this internal foundation. Reads and mutations are audited, and changed/currently inaccessible document metadata is redacted on list. The status check returns `STALE` or `INVALID` for changed metadata or lifecycle and otherwise `UNAVAILABLE`, never a verification fingerprint. A source row lock, unique active slot, document-identity uniqueness, expected version and event request key guard races/retries; a replacement uses a new document row, and failed audit writes roll back the transaction. Synthetic MySQL tests cover those guarantees for the narrow fixture only.

Every link remains `UNAVAILABLE` for verification: stored checksums are untrusted claims, not proof of private immutable bytes or a source-approved evidence type. No upload, content retrieval, member self-service, exception-case association, or trusted controlled-posting adapter is exposed. Other financial and payment sources are unsupported. The repository is not mounted to any production endpoint and must not be integrated into posting until source-writer serialization, immutable object identity, actor/job authorization, document-version history and S3 controls have been independently designed and tested.

The existing document upload service now persists the SHA-256 calculated from validated upload bytes for new documents; no historical checksum is fabricated. The G0 attested structure includes the checksum column, while the 20260814 simplification migration historically dropped it, so installation ordering and target compatibility require verification. A stored digest is not proof that the current object is immutable, private or unmodified, and it does not grant an evidence verification result.

Concurrent receipt attempts previously wrote the same object key; a synthetic eight-worker test demonstrated that the linked checksum could disagree with the final bytes. Receipt attempts now use unique UUID keys and request an exclusive write (`wx` locally; conditional `If-None-Match: *` for S3-compatible providers). Each claim increments the locked receipt's `attempt_count`; finalization, failure and failure notifications require that exact current generation. Synthetic tests exercise an older worker failing while a newer worker is processing, late failure after generation, and eight simultaneous attempts.

The additive `20261107_receipt_attempt_recovery.sql` introduces `payment_receipt_attempts` and append-only-through-service `payment_receipt_attempt_events`. A unique object key and `(receipt, attempt number)` identify `PREPARED`, `STORED`, `FINALIZED`, `FAILED` or `SUPERSEDED` attempts. The prepared row is committed before any upload; a crash can therefore leave a `PREPARED` entry whose object may or may not exist. Stored rows record the bytes' upload digest and size, not proof of an immutable private object. The receipt's current `document_id` and a FINALIZED attempt link identify the winner; retry claims a new generation. Duplicate queueing preserves an active `Processing` state. An unmounted Chairman-only internal inspection repository locks the receipt and attempts, audits access, and reports recorded states and whether a document is linked; object availability is always `UNKNOWN` and raw keys are not returned. Pending and superseded entries are retained for investigation. **No automatic deletion, abandoned classification, cleanup endpoint, retention duration or claim that a stored object exists is implemented.** A privileged, authorized recovery workflow must later verify active workers, source/document links and object identity before any cleanup. Existing receipt rows are not backfilled. The migration is mandatory before the new receipt service is deployed; older schemas without it will not process new attempts. It was run only on synthetic MySQL, not a live target. Losing or interrupted attempts can still leave protected objects. Conditional S3 request construction has a local contract test, but backend support, access policies, versioning and object immutability are not established by it.
